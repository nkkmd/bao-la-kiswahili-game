# ユーザー選択の確定 — 改訂契約の設計方針

## 確定した範囲

ユーザーの「推奨の選択でお願いします」に基づき、[採否判断案](ADOPTION_DECISION_PROPOSAL.md)の推奨事項を、今後の改訂契約を具体化する設計方針として採用する。これは推奨のまま保留する記録ではなく、**以下の選択が確定した記録**である。

一方、B1数値一式・Actions候補001を含む実行契約全体の採用、技術的な準備成立、実装・新規試験・科学登録/実行は含まない。今回の認可は選択の記録と文書整合までであり、実装移行停止は解除しない。

照合したmainは`1205afe0a2c79c957f5d21bee6b7de47a6665ae4`、選択対象の資料headは`b22fc5ebac2a34ab12989f01109a7edf7903e104`。PR #236はdraft・未統合である。開始時の追跡済み差分はなく、既存一時ファイル5件を保持する。過去の未採用表示は、その時点の資料状態として残し、現在の選択は本書を優先する。

## 採用する設計方針

| 項目 | 確定した選択 | 保持する条件・影響 |
| --- | --- | --- |
| 計数範囲 | 準備P・科学M・保全Rを分け、制御Cと基盤Kの費用も示す | 旧単一20分/1 GiB/256 MiB契約の成立とは扱わず、総費用を過小報告しない |
| 科学上限・正確性 | 科学M20分・1 GiB・swap 0・256 MiB、内数の終了予約180秒/16 MiB、領域上限・独立検算を維持 | 初回科学codeロード・遮断集合構築・lease/consume・科学保存・独立検算はM内。Rで科学処理を完成させない |
| 一度限り性 | 全区画lease、PRNG初期化前のdurable consume、attempt 1、中断後の科学再実行禁止を維持 | 科学操作のretry・救済・追加source・候補差替えを許可しない |
| 保存client | 既存JSON clientの直接流用を採用せず、raw読戻しと有限bufferの専用clientを設計する方針 | 48 MiB以下・最大6片・圧縮合計256 MiBは増やさない。既存clientは変更せず、新実装はまだ行わない |
| 通信予算の予約 | 1 GiB内で最終D600 MiB、最終制御16 MiB、registry/consume/mirror等408 MiBに配分 | D metadata合計2 MiB以内を設計条件にする。結果後に未使用分を科学処理へ戻さない。408 MiBが先に効く早期停止も保持 |
| 最終受領 | Tへの最後のref作成201と期待ref/commit一致をU_apiとし、Sの観測reportをKの来歴へ残す | 強い保存側の独立durable receipt・物理fsync・指定server時刻の保証は要求しない。保証範囲を限定する選択である |
| 停止証拠 | M/R補助子孫のOS側停止証拠EをTへ結合し、S/K自身の終了は基盤側の来歴とする | S自身の終了を必須Eから外す。M/R子孫の停止は省略せず、job終了表示だけで代用しない |
| 不明・欠落の扱い | 記録欠落時は未確認・未ACKを保持する | 後日Tのrefが見つかっても実行内U_api受領へ昇格させない。A_D、E、T保存、U_api観測、S終了を分離する |
| 環境比較 | 標準Actionsを第一比較候補として維持する | 環境の正式選定や成立認定ではない。WSL/custom runnerへ自動移行しない |

選択したU_api方式では、S自身がT blob→tree→commit→新規refの4 POSTを行う方向を採る。どこかで失敗・応答不明なら再発行しない。まだ返っていないU_apiをTへ入れず、Tを再送して最後のACKを取り込む反復もしない。Sのreportは独立した受領証明ではないという信頼境界を受容する。

## 文書・保存監査
