# 送信境界と設定移管の方式比較

## 今回の判断

2026-10-30、main `80b0ffe279f97527cf04478ec14d69ce404d11df`と[配布runtimeの記録](runtime-components-20261030/README.md)を照合した。未統合PRと追跡済みファイルの差分はない。開始時の未追跡一時ファイル3件は変更・追加対象から除外した。

実装へ進める経路は未成立である。比較の優先候補を、**runner/workには外向き通信を許さず、限定IPCの先の専用送信主体が取引を管理する方式**とする。ただし送信主体が未改変.NET transportを呼ぶだけでは内側retryが残る。通信の権限分離と一度限り送信は別条件であり、この候補の採用・実装・成立を認定しない。

次は候補の最小protocolと設定対応を静的に詰め、全入力・容量の下限を先に評価する。容量または認証の適合が閉じなければ成立不足として停止する。runner改変・build・登録・実行、新規remote結合試験は開始しない。

## 同じ条件で比較した方式

| 方式 | 内側retry | 子process等の迂回 | 設定・容量・来歴 | 処置 |
| --- | --- | --- | --- | --- |
| 未改変.NET transportの外側guard | 最初の失敗を外側が見る前に再試行し得る | source上の差込みだけでは防げない | 既存設定を残せても無再送の条件が閉じない | 成立方法として除外 |
| 通信を別主体へ移し、そのまま標準transportを使用 | 同じ内側retryが残る | 権限とIPCが実証できれば隔離の候補 | proxy等を移管する必要があり、新主体の費用も加わる | 単独の解決方法として除外 |
| .NET runtime改変とrunner全clientのguard | HTTP認証・redirect・全protocol分岐まで修正範囲が及ぶ | 別途OS境界が必要 | runtime/build入力、binary対応、全依存・容量が未確定 | 比較対象として保留。改変・buildしない |

HTTP/1.1固定、接続再利用禁止、redirect無効のいずれか一つだけで無再送を認定しない。接続開始の失敗、送信途中、header成功後のbody欠落、認証challenge、version fallbackを分けて扱う。既存jobでretryが起きたという判断は加えない。

## IPC取引の最小契約案

これはメッセージ形式の設計案で、実装schemaや実行認可ではない。runnerが任意の宛先・再試行を要求できる汎用proxyにしない。

| 内容 | 必須条件 |
| --- | --- |
| 呼出主体 | peer識別と実行ID・固定job/head/attemptを照合。子が親・保存主体を名乗れない認証方法を固定する |
| 取引識別 | 親が発行した許可ID・phase・操作種別・事前に固定した対象を結合。同じURLでも正当な次のlong pollとretryを区別する |
| 要求 | method、宛先、許容header、bodyのbyte/hash、最大応答byte、期限を固定。callerの任意headerでcredential・宛先を差し替えない |
| 秘密 | credential/tokenは値をlogへ出さず、参照と使用主体を限定。runnerから仲介主体への任意秘密転送を既定にしない |
| 許可消費 | 送信前に親の容量予約と一度限り消費を確定。記録不能なら未送信で停止し、再起動後も使用済み許可を復活させない |
| 応答 | headerだけで完了しない。body上限・hash・構文・操作ごとの成功条件を検査し、完了通知を許可IDへ結合する |
| 意味検算 | callerの意味検算が必要なら、検算者と完了通知を認証し、検算終了まで次の通常許可を発行しない。通知欠落は未完 |
| 取消・故障 | 期限、IPC切断、送信主体の停止、body欠落、検算失敗を不変の最初の理由へ記録。失敗取引を新IDで再発行しない |

通常は同時に1取引とし、long poll中に別の制御通信が必要な場合は、そのprotocol順序との適合を先に調べる。直列化でjobが進まなければ設計不足であり、無検証の並列化で解消した扱いにしない。送信中のbufferとspoolも同じ資源予算へ含める。

## 許可と停止の順序

1. 親が未使用許可を作り、対象byteと保存費用を予約する。送信主体は同じ許可の取得を原子的に確定する。
2. 送信前の使用済み記録が確定してから送信を開始する。送信後に記録を追い付かせる順序は認めない。
3. 応答bodyと必要な意味検算が完了するまでは取引を閉じず、次の通常通信を許可しない。
4. 最初の失敗で通常許可を閉鎖する。送信有無が不明でも同じ取引を再送しない。IPC再接続や別clientからの新規要求で解除しない。
5. 故障後の保存は、別に事前固定した対象・保存先・要求数・byte上限の専用許可だけで扱う。通常の取得や失敗保存の救済には使わない。
6. 最終保存の応答不明は未ACK、停止未確認は未完成とする。remoteに何も残らなかったと推測して容量予約を返さない。

電源断等からの自動復旧・retryをこの設計で認可しない。使用済みの不変記録と、保存が失敗したprefixを区別して保持する。

## 設定移管で決める項目

[既存型分岐の調査](runtime-20261030/README.md)では、Vss/Rawは最内側handlerをHttpClientHandlerへ型変換して設定する。別型transportでは設定が自動移管されない。移管先を送信主体に限定し、次の項目ごとに「同じ意味で対応」「事前契約により明示拒否」「未対応」を分類する。未対応を既定値へ落として成功扱いにしない。

| 項目 | 固定すべき扱い |
| --- | --- |
| proxy | 宛先・proxy認証・bypass・環境由来設定を列挙。接続先変更や別proxyへのfallbackを黙認しない |
| server証明書 | 名前・chain検証・trust inputを固定。任意callbackを別processへ転送できると仮定せず、検証無効化で代用しない |
| client証明書 | 対象接続と秘密鍵の使用主体・所有権・破棄方法を固定。保存証拠に秘密鍵を入れない |
| HTTP認証 | bearer、challenge、token更新の必要順序を操作別に確認。401後の自動再送を未レビューの基盤通信へ移さない |
| redirect | 自動追跡を成功へ含めず、必要なら対象と各取引の許可・失敗条件を実行前に定義する |
| cookie・圧縮 | cookie状態の有無、圧縮bodyと検算対象byte、展開後上限を固定。展開量を計数外にしない |
| timeout・取消 | 共通20分と終了予約180秒に従い、caller切断後に送信主体が孤立してworkを続けない |

全clientのbody完了点、認証provider、Gitのsmart HTTP等の必要protocolは未監査である。有限の許可台帳へ収まることが確認できなければ、この候補も採用しない。既存Git保存やActions来歴を、別protocolへ無言で置換しない。

## OS境界と最終保存

runner/work側の外向きsocketと継承された通信FDを拒否し、許可されたIPCだけに閉じる。親監督・送信主体・runner/work・保存処理は同じ親資源予算内で権限を分ける。ネットワーク境界、manager/daemon socket、cgroup書込、sudo等の拒否を具体設定と原証拠で示すまで実効性を認定しない。ユーザー用unitのDelegate=yesだけでは成立しない。

原image封印後のjournal、送信主体の停止記録、全子停止、最終receiptの終端を同じ時計へ置く。receipt自身をそれ以前の原imageへ含める循環条件は作らず、どの対象までACK済みかを固定する。送信主体終了後に計数外の別uploaderを起動しない。最後の記録を誰が閉じるかは未解決のままで、完成を宣言しない。
