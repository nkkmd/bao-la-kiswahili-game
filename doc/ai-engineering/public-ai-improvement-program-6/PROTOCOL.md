# PBAI-P6 — 事前に固定する検証条件

## 問いと結論の範囲

学習した論理ゲート型評価器をAI-GEN3の探索へ組み込むと、同じ持ち時間で棋力が改善するかを調べる。対象は今回の符号化、教師、モデル規模、学習量で構成する一候補であり、失敗しても論理ゲート型AI全般を否定しない。

数値設定の正本は[SPEC.json](SPEC.json)。開始判断は[開始レビュー](AUTHORIZATION_REVIEW.md)。本契約と実装の固定前には新規データ・学習結果・速度測定・対局成績を生成しない。人工入力と既知局面によるソフトウェア試験は準備段階で実施できる。

## 候補と比較対象

| ID | 役割 | 固定した構成 |
| --- | --- | --- |
| PBAI-C012-v1 | 棋力強化を検証する主候補 | 3層、各512個の学習可能な2入力論理ゲート。各ゲートは16真理値表から選択 |
| PBAI-C013-v1 | 学習の効果を比較する参照候補 | 同じ入力のridge線形回帰 |
| PBAI-C014-v1 | 通常の小型学習器との比較 | 同じ入力、隠れ32ユニットのtanhネットワーク |
| AI-GEN3 | 現行の比較基準 | SPECのcommitと公開ソースhash、軽量遷移有効のhard/bao/phase2 |

候補は1方式1初期値・1学習設定のみ。参照候補の結果を見て主候補を取り替えない。ゲートは連続緩和で学習後、最大logitの真理値表へ離散化する。離散化後の512出力に対し、学習データだけでridge読み出しを再推定する。読み出し係数と切片を4096倍して整数化し、JavaScriptの論理演算と整数係数の加算で実行する。これは**学習したゲート特徴と整数の線形読み出しを組み合わせる評価器**であり、全演算がBooleanゲートだけで完結する実装ではない。

各ゲート層は元入力と直前層から固定乱数で2入力を選ぶ。学習するのはゲート種類と読み出しであり、配線は固定する。150 epochの最終状態だけを使い、開発用成績によるepoch・初期値の選択をしない。線形・MLP・ゲートには同じ教師、同じ両視点の標本を与える。モデル容量や最適化条件は同一ではなく、一般的な方式優劣の証明とはしない。

## 局面の表現

盤面は評価側、相手側の順に並べるが、穴のインデックスは元のままとする。絶対的な評価側の番号も保持し、未検証の鏡映・回転対称性は仮定しない。

- 各32穴: 石数の7bitと、1・2・4個以上の3閾値。320入力。
- 両者の持ち石: 各5bit。10入力。
- 両者のpending累積値: 各32bit。64入力。
- 両者のnyumba所有: 2入力。
- 評価側が手番か、絶対評価側番号、Mtajiか: 3入力。

合計399個のBoolean入力。数値を範囲外で丸めたり黙って切り捨てたりしない。turn・表示reasonは評価入力に使わず、RAW状態と棋譜には保持する。終局は既存エンジンのwinnerを厳密に処理する。

両視点の予測差の半分を取り、1024倍した値を整数方向へ切り捨てて評価値とする。これにより評価側を交換したときの符号反転を構造的に保証する。Boolean符号化、両視点の評価、整数読み出しの費用を速度測定に含める。

## データ生成と分離

標準初期局面から合法variantをMulberry32による一様乱数で選び、最大96手まで生成する。seedの偶奇でNamua/Mtajiを割り当て、Namuaの12〜40手、Mtajiの44〜88手で最初に合法variantが2個以上ある非終局局面を一つ採用する。評価値・対局結果によって選ばない。

| 用途 | seed block先頭 | 固定標本数 |
| --- | ---: | ---: |
| 学習 | 831000001 | 各phase512、計1024 root |
| 開発用評価 | 832000001 | 各phase64、計128 root |
| 独立検証用評価 | 833000001 | 各phase64、計128 root |
| 開発用対局 | 834000001 | 各phase16ペア、計64局 |
| 独立検証用対局 | 835000001 | 各phase32ペア、計128局 |
| 最終holdout対局 | 836000001 | 各phase128ペア、計512局 |

各生成blockは先頭から8192 seedまで。必要数に達すれば終了し、不足時は追加せずHOLDとする。学習初期化は837000001と838000001、統計再標本化は839000001。既存doc/tools/test/artifactsにこれらの先頭seedの使用記録がないことを確認した。先頭値検索だけで全研究の全乱数列との非重複を証明したとは扱わない。

1系列1rootとし、RAW hash、最初の12手のprefix、全source着手系列hashをsplit内外と[既知識別情報](KNOWN_IDENTITIES.json)に対して重複排除する。棄却seedと理由も残す。両視点の標本は必ず同じsplitへ置く。採用rootへ至る全着手を保存し、独立再生で到達可能性を確認する。標準初期局面および12手未満の共通prefix、異なる系列の未採用局面での合流は除去を保証しない。

教師はAI-GEN3の固定D3・時間制限なしのrootScoreを1024で割って[-1,1]へclipした値。相手視点のラベルは符号を反転する。教師は近似的な探索値であり、真の勝率・最善手・ゲーム理論的価値ではない。今回は探索値の蒸留に限定し、自己対局による教師の改善は追加しない。

開発用データは学習スクリプトへ渡さず、最終epochのモデルを保存してから評価する。validationとholdoutは先行条件が成立するまで生成しない。公開済みの過去研究データを学習・検証へ混ぜない。

## 事前診断と正確性

開発用の各phase先頭16 rootで、AI-GEN3評価中の合法手生成・捕獲手適用の時間と呼出数を計測する。計測器付きの値は費用構造の参考値であり、速度比較には計測器なしを使う。診断を見て今回の候補構成を変更しない。

ゲート全16種類の真理値表、Boolean入力と独立した復号、Python出力とJavaScriptの整数評価、両視点符号反転、入力非破壊、終局符号、評価器未指定時の固定D2探索の選択手と時間以外の全統計一致を確認する。線形・MLPも同じ探索差し替え口を使う。公開sourceのbyteは一切変更しない。

学習データ全件の保存済み出力をPython/JavaScript間で照合する。ゲートと整数線形評価は完全一致、MLPは整数化前の浮動小数誤差による最大1点差を許容する。教師の再計算は時間制限なしの同じ固定source・D3で全件照合し、時間統計は比較しない。

## 段階的な判定条件

開発用および独立検証用の評価では、次をすべて必要とする。

1. 主候補の教師に対する平均二乗誤差が、現行静的評価の誤差の1.10倍以下。
2. phase別のroot時間比の中央値が0.90以下、全rootの時間比のp95が1.10以下。
3. 既存8戦術fixtureが指定深度で全件通過。既知問題への回帰条件であり、人間の最善手の証明ではない。
4. エンコード・出力・ソース・合法手に不整合がない。

速度は各rootで各方式2回warmup、6反復、各反復20評価。baseline、logic、linear、MLPの実行順を循環させる。単一プロセスで測り、入力符号化と両視点の評価を含める。強制GCはせず、root別反復中央値を単位とする。単一局面の遅延を測るもので、大量バッチの処理能力とは分ける。

評価条件を通過した主候補だけが対局へ進む。開発用・独立検証用対局は全体勝点率0.45以上、各phase0.35以上、crash/illegalなし、期限超過率のbaselineからの増加0.05以下を次段階条件とする。

主候補が条件を満たさなければ、その固定候補は`DEVELOPMENT-GATE-FAIL / HOLD`または`VALIDATION-GATE-FAIL / HOLD`。後続splitは開かない。これは今回の候補が次段階に適格でないという意味であり、未実行の正式棋力試験で敗北したことを意味しない。実装不整合・資源上限・不完全な保存は`TECHNICAL-INVALID / HOLD`とし、学習方式の否定結果に読み替えない。

## 対局・最終判断

両者ともhard/bao/phase2、軽量遷移有効、100ms/D8。root準備後にdeadlineを開始する公開実装の挙動を保持し、呼出全体の時間も記録する。学習評価器だけを変更するため、評価器を使う既存の着手順序付けにもその変更が及ぶ。評価と順序付けの別々の寄与は今回識別しない。

同じrootで担当sideを交換して2局1ペアとする。開局後160手到達のみ引分0.5点、winnerは1/0点。ルールのrelay-limit判定を引分へ変更しない。完全な着手・探索統計・最終RAWを保存し、別処理で全棋譜の合法性と得点を再構成する。反復による勝敗規則を追加しない。探索呼出全体が150msを超えた割合を両者で比較する。

最終512局、各phase128ペア、独立cluster200以上を必要とする。同一対局系列を共有する先後ペアは連結してclusterにまとめ、phaseを保つcluster bootstrapを10,000回行う。主要値はphase均等の先後ペア平均勝点。勝点率0.53以上、両側95％区間下限が0.50超、各phase0.45以上、正確性・戦術・運用条件通過なら`STRENGTH-IMPROVED-IN-FROZEN-DOMAIN`。それ以外は`STRENGTH-IMPROVEMENT-UNCONFIRMED / HOLD`。途中成績で標本数を増減しない。

これはNode/Linux上の100ms/D8という固定範囲の工学検証である。スマートフォン実機、標準500msでの棋力、一般的な最善手、ゲート方式そのものの優越性を証明しない。参照モデルは予測誤差・速度・既知戦術で比較し、主候補との対局リーグは今回行わない。

## 資源と再開

NumPyによるCPU学習、Nodeによる探索・評価、各工程1スレッド、Node heap上限2048MiB。全実行と検算を外側のPython監視器が連続4時間で監視する。学習や探索とは別プロセスから期限停止できるようにする。開始前にソースをcommitし、開始markerの排他的作成とハッシュ照合を必須にする。

同一runの再開始・上書き・失敗後のseed追加は禁止する。失敗時は完成済み証拠を保存し、未完了はHOLDとする。チャットが中断しても監視器が生存していれば継続する。プロセスが死亡した場合は開始markerを消してやり直さない。成果物は各工程で書き出し、ブランチへ保存する。

失敗後に今回のデータで試作を修正する場合、そのデータは既知の開発用として明示し、新しい候補・契約・未使用の評価集団を用意する。過去の正式結果を救済的に変更しない。
