## 組込み確認時点の状態

採用レビューを受け、hard向けの組込みを[PR #127](https://github.com/nkkmd/bao-la-kiswahili-game/pull/127)へ用意した。依存先は採用レビューの[PR #126](https://github.com/nkkmd/bao-la-kiswahili-game/pull/126)。候補は**既定無効**であり、正式採用、main統合、公開配備、AI世代更新は行っていない。公開AIは`AI-GEN3 / AI-GEN3-RELEASE-001`を維持する。

## 組込みの内容

| ファイル | 役割 |
| --- | --- |
| `public/logic-evaluator.js` | P9の静的評価器とbyte単位で同一の固定モデル |
| `public/ai-candidate.js` | P9の候補探索。公開するJavaScript名だけを`BaoCandidateAI`に変え、基準AIと共存させる |
| `public/ai-release.js` | hard・既定`bao`／`phase2`への限定、既定無効の設定、候補と基準の選択を一か所で行う |
| `public/ai-release-worker.js` | 共通の選択処理をWorker内で呼ぶ。検証用の乱数固定処理は含めない |
| `public/main.js` | Workerと失敗時の直接実行から、共通の選択処理を使用する |
| `public/diagnostics.js` | 候補識別子と基準AIへの復帰の有無を保存する |
| `public/index.html`、`public/service-worker.js` | 読み込み順と保存対象を揃え、キャッシュをv34へ更新する |

hardでも独自の重み・補正や別profileを指定した場合は候補を使わない。easy、normal、expertは基準AIを使う。モデルまたは候補探索を取得できなかった場合も基準AIへ戻り、要求が候補を指定していた場合は診断の`evaluationCandidate`と`evaluationFallback`へ記録する。

AI-GEN3の正式資産である`engine.js`、`ai.js`、`ai-weights.js`、`ai-config.js`、`ai-worker.js`の5ファイルは変更していない。P9のモデル・探索を調整せず、乱数、探索時間、探索深さ、ルールも変更しない。今回の分離構成は公開経路へ接続するためのもので、棋力を再測定した結果ではない。

## 確認方法と結果の意味

Nodeでは、既知9局面の凍結参照とWorker・直接実行の一致、候補無効時の一致、モデル未取得時、対象外設定、診断の保存を確認する。既存のリリースhash、エンジン、AI、探索、戦術、Worker、設定、表示、SEO、軽量遷移の回帰も対象にした。公開資産の新しいキャッシュ番号を検査する2試験だけ期待値をv34へ更新し、正式リリースのhash条件は変更していない。

ブラウザ試験は、公開用ファイルをローカル配信し、検証用の応答で`ai-release.js`の既定無効フラグを有効にする。切戻しではフラグを無効へ戻し、Service Workerのキャッシュ名を検証用v35へ変える。その他の候補コードは同一である。配信元への接続を切る条件でキャッシュからの再読込みを確認し、端末の機内モードを操作した試験とは区別する。

試験では、候補の着手、3回の継続応答、新規対局後のexpert、Worker開始後の取消、配信元への通信不能、更新後の切戻し、Worker未対応・エラー時の直接実行、モデル未取得時を確認する。継続応答の人間側の手は画面の`playMove`経路へ合法手を渡しており、タッチ操作の精度や長時間の使用感を評価したものではない。

## 準備中の修正履歴

最初の組込み案は既存AIへ直接差し替え口を追加したため、正式リリースのhash検証で停止した。保護条件を緩めず、候補を別ファイルへ分離し、正式資産のbyteを保持する構成へ修正した。

ブラウザ試験の準備では、非同期のキャッシュ削除を待つ方法と、Workerにもモデル取得失敗を確実に与える方法を修正した。ブラウザAPIによるオフライン模擬で再読込みエラーが出た実行も保存し、配信元が応答しない条件を明示した別の確認に整理した。これらは既知局面と操作の試験準備であり、P8・P9の正式対局の再実行や結果の救済ではない。

## スマートフォンで確認する手順

リポジトリの作業ブランチ`engineering/pbai-c015-hard-integration`を取得したPCで、次を実行する。生成先が既にある場合は別の空のディレクトリを指定する。

```sh
node tools/engineering/prepare-pbai-c015-preview.cjs
python -m http.server 8765 --directory artifacts/local/pbai-c015-preview
```

この処理はpublicを変更せず、hardの候補フラグを有効にしたコピーと、各ファイルのSHA-256を含む`PREVIEW.json`を作る。簡易HTTPサーバーでもキャッシュの保存対象を取得できるよう、`privacy.html`と同じ内容を拡張子なしの`privacy`にもコピーする。公開サイトへこのコピーを配備する手順ではない。PCではlocalhostのポート8765、同じネットワークのスマートフォンではPCのLANアドレスのポート8765を開く。

HTTPのLANアドレスではService Workerが利用できない場合がある。この方法で確認するのはオンラインでの実機操作と応答であり、オフライン利用・PWA更新はHTTPSの検証用配信など、Service Workerを利用できる条件で別途確認する。画面の世代表示は基準系統のAI-GEN3のままなので、候補を使用したことは診断記録の`evaluationCandidate: PBAI-C015-v1`で確認する。

1. hardを選び、先手・後手の両方で開始してAIが着手することを確認する。
2. 人間側を数手操作し、応答、表示、入力の詰まり、端末の発熱などを記録する。
3. AIの思考中にNEW GAMEを押し、新規対局へ古い応答が混ざらないことを確認する。
4. expertやnormalへ切り替え、候補が使われないことを診断で確認する。
5. AI改善用診断から「AIの手を記録」「記録を保存」を使い、結果JSONを保存する。

端末名、OS、ブラウザとバージョン、日時、`PREVIEW.json`、保存した診断、試した操作と問題の有無を一緒に残す。`sourceTreeDirty`がtrueの場合は未コミット変更を含むため、そのコピーだけで正式な配備対象を確定せず、コミット済みの同じ内容で確認する。端末の実測を得るまで、スマートフォン確認済みとは扱わない。

## 切戻しと次の判断

採用後に切り戻す必要が生じた場合は、`ai-release.js`の`PBAI_C015_ENABLED`をfalseへ戻し、現在配信中とは異なる新しいService Workerのキャッシュ名を使ってpublic一式を再配信する。旧・新ファイルを混在させず、更新後の候補無効、AI着手、キャッシュ更新を確認する。今回のPRでは既にfalseであり、切戻しそのものを実サイトへ実施したわけではない。

残る実機確認を終えた後に、hard限定の正式採用と公開切替を別途判断する。expertの棋力、長時間の実機操作、すべての端末での性能は今回の成功から一般化しない。[採用レビュー](README.md)とP8・P9の正式判断を保持する。
