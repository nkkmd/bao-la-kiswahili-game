## AIと過去の証拠の扱い

公開系統はAI-GEN4を維持する方針とする。takasia対応の改訂記録を別に設け、既存release IDや採用判断を過去へ遡って書き換えない。新しい改訂IDの発行は実装・検証後に行う。

現行論理ゲート型評価器にはtakasiaの入力がない。初期実装では学習済みモデルを維持し、探索が新しい合法手と遷移を使う状態を作る。その後、通常局面とtakasia局面を分け、公開hard・expertの低・標準・高予算で品質と処理時間を確認する。補正・再学習が必要と判明した場合は、別の比較条件と判断記録を用意する。

対局比較では両AIを同じ新ルールで動かす。旧ルールAIと新ルールAIの勝率を棋力改善の証拠にはしない。長時間試験はGitHub Actionsを第一候補とし、局ごとの出力、実行条件、完了済み局の識別、再開方法を保存する。局数・seed・採否閾値は実行前に別途固定する。今回の準備は対局試験の実行・合格を含まない。

過去の固定資産、checksum、評価器モデル、先後差研究、Jev比較の結果を保持する。旧資産との完全一致を要求する試験は、当時の固定版を検証する役割を残し、現在の新しい改訂版の挙動検証を別に追加する。既存の厳格な検査を削除して通過させない。

## 再開位置

工程4のAI-GEN4対応を実装・検証中である。[AI検証条件](AI_BENCHMARK_PROTOCOL.md)で12局面・72予算条件を固定し、Actionsで計測する。[工程3の実装記録](ENGINE_IMPLEMENTATION.md)を読んでから、局面キー・探索キャッシュ・Worker引渡し・切戻しを更新する。同じ石配置でもtakasiaの対象有無が異なる局面を区別し、全難易度の着手を新エンジンで再検証する。

工程3の検査は次のコマンドで再実行できる。

```bash
node tools/takasia/check-engine.cjs
node --test test/takasia-contract.test.cjs test/takasia-engine.test.cjs test/engine.test.js test/namua-mtaji-transition-engine.test.js
python3 tools/takasia/verify.py
```

局面識別・棋譜などが揃う前に新状態を公開画面へ配信しない。ユーザーの継続指示に基づき、工程3を準備ブランチとDraft PRへ追加した。main統合・配信・新しい公開releaseの発行は行っていない。
