# expert検証：長時間実行の対策

## 今回実装した対策

チャットの実行セッションを長時間試験の唯一の実行基盤にしない。独立したGitHub Actionsの2ジョブで、保存点の生成、外部成果物への保存、別ジョブでの取得、SHA-256と出自コミットの照合を行う事前確認を追加した。

実装は`tools/engineering/test-expert-durable-runner.cjs`と`.github/workflows/expert-durable-runner-preflight.yml`である。既知初期局面の合法な1手だけを用い、棋力用seedは消費しない。改ざんと出自コミット不一致を拒否する。ローカルの生成・検証は成功した。GitHubのジョブ間確認結果は後続のCI記録に保存する。

これは実行基盤の小規模な確認であり、12時間の耐久試験や新しいexpert棋力試験の完了ではない。GitHub側の障害や上限をなくすものでもない。

## 次の独立試験へ必要な変更

次回の正式実行前に、以下を別の契約として固定する。

1. P10を技術的無効として保持し、既知集合に今回の全source採否記録を追加する。新しい未使用seedブロックを予約する。
2. 先後ペアを完了してから保存する小さなバッチに分け、各バッチを独立ジョブで実行する。直前バッチの成果物とhashを確認してから次へ進む。並列対局によるCPU競合は持ち込まない。
3. 実行器・設定・モデルのhash、承認された実行ID、seed消費台帳を照合する。Actionsの再実行や新しいrun IDによって消費済み集団が再測定されないよう、seed消費前に永続的な開始記録を作る。
4. 全体期限は最初の開始時刻から管理し、ジョブの待機時間と最終検算も含める。各ジョブの上限内に収まるバッチ数と最悪所要時間を計算する。途中で期限を延ばさない。
5. 完了済みバッチの保存と未完了対局の扱いを区別する。途中の対局を再測定して同じ正式結果へ戻さない。失敗時は事前規則に従ってHOLDとする。
6. 棋力試験前に、既知局面だけで開始記録の二重作成拒否、依存ジョブ失敗時の停止、成果物不足・破損、全体期限を確認する。

上記の正式試験用バッチ実行器と新規seed契約はまだ作成・凍結していない。今回の2ジョブ確認をその完成と読み替えない。採用条件・候補の調整やP10の部分結果による選択は行わない。
