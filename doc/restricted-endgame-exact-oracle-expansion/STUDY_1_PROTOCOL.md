## 9. Complete forward closure contract

An exact-oracle claim requires complete forward closure.

For every domain state:

1. enumerate the exact complete legal-move set;
2. generate every successor RAW state;
3. classify every successor as normative terminal or a member of the exact domain closure;
4. preserve exact node and edge identity;
5. preserve complete predecessor relations;
6. prove that no nonterminal legal successor is omitted.

A structural root filter is not a successor-pruning rule. Once a root is admitted, the exact scientific domain is its prospectively defined complete closure unless the later formal domain contract explicitly defines another closed set and proves closure.

The following must remain distinct:

```text
CLOSED
OPEN / ESCAPING
INCOMPLETE-DOMAIN
RESOURCE-CUTOFF
TECHNICAL-INVALID
NON-ESTIMABLE
```

A nonterminal successor outside a nominal structural filter does not disappear; it either becomes part of the closure or prevents the proposed filtered set from being called closed under the prospectively frozen domain definition.

Near-complete is not exact.

## 10. Terminal semantics

Terminal classification must be rule-semantic and independently reconstructed.

Implementation safety reasons, administrative stop reasons, artifact truncation, and resource cutoffs are not game outcomes.

Where a terminal state is represented, the exact solver uses absolute-winner semantics rather than assuming that post-terminal `state.player` alone defines WIN/LOSS.

## 11. Retrograde semantics

Exact retrograde analysis is permitted only for a closure-complete domain.

Base class:

```text
TERMINAL + absoluteWinner
```

Nonterminal fixed-point classes:

```text
WIN  = player-to-move has at least one successor resolved to that player's win
LOSS = all successors resolve to opponent win
RECURRENT = unresolved after the exact WIN/LOSS fixed point
```

At Study start, `DRAW` is not an authorized synonym for `RECURRENT`. Current frozen Bao semantics do not provide a prospectively established repetition/draw rule for this endpoint. A cycle alone is not automatically labeled a draw.

## 12. Distance contract

Default exact distance metric is legal-move/ply `DTF` (distance-to-forced-terminal):

```text
TERMINAL = 0
WIN = 1 + min DTF(winning successors)
LOSS = 1 + max DTF(all opponent-winning successors)
RECURRENT = null
```

The winning side minimizes terminal distance; a losing player maximizes resistance. No result-dependent distance definition change is authorized.

If Stage 2 introduces any additional distance quantity, its semantics must be separately frozen before outcome.

## 13. Optimal move contract

For every resolved nonterminal state, the result must preserve:

```text
all optimal moves
optimal-move multiplicity
exact move identities
successor bindings
```

For WIN, optimal moves are all moves attaining the prospectively frozen winning distance rule. For LOSS, the maximum-resistance move set is preserved under the loss-distance rule. RECURRENT optimality requires a separately frozen rule and is not invented after observing cycles.
