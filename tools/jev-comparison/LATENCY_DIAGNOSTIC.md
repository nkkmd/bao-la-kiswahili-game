# Jevの通信遅延の追加診断

作成日: 2026年9月21日。診断識別子: `latency-diagnostic-v1`。

## 予備対局で確認したこと

キット0.1.0の予備対局は、最初の対局の5手目で一時停止した。Jevへの3要求がすべて500msの応答待ち上限に達し、3回連続の代替処理で停止する条件が働いた。Jevの回答を対局の探索順序に使えた着手は0であり、完了した対局も0である。勝率や強化の有無を判定できる結果ではない。

| 項目 | 確認結果 |
| --- | ---: |
| API呼び出し累計 | 20回（接続確認1回、局面試験16回、対局3回） |
| 対局中のAPI待ち時間 | 501.415ms、501.621ms、503.323ms |
| 使用量が返った分の計算額 | $0.001117326 |
| タイムアウト3回分の予約額 | $0.008257536 |
| 予約分を含む累計計上額 | $0.009374862 |
| 候補側の探索時間 | 約1.44〜1.46秒／着手 |
| 候補側の総所要時間 | 約2.000秒／着手 |

棋譜5手を基準エンジンで再生し、各手の合法性、局面ハッシュ、保存された最終局面の一致を確認した。20件の送信内容・応答・費用集計も整合した。前回受領した局面試験の記録は、進捗集計を除いてすべて同一である。

直前の局面試験では、最初の2件が約0.93秒、残り14件が約0.25〜0.39秒だった。今回の500msでの打ち切りからは、本来の応答完了時間を測れない。接続状態、要求の間隔、入力、サービス側の状況などの影響は未特定である。

## 次に測ること

対局を再開する前に、以下の8要求だけを別の診断として実行する。既存のタイムアウトを自動再試行する処理ではなく、入力と件数を固定した追加測定である。

| 条件 | 入力 | 件数 | API応答待ち上限 |
| --- | --- | ---: | ---: |
| 連続送信 | タイムアウトした3局面、成功済みの局面試験0番 | 4 | 各5秒 |
| 間隔を空けた送信 | 上と同じ4入力・同じ順序。各送信前に4秒待機 | 4 | 各5秒 |

先に連続送信、次に間隔を空けた送信を行う。最初の要求は、新たに起動したプロセスからの送信として記録する。4秒は対局中の要求間隔に近い条件を調べるための目安で、対局のCPU負荷を再現する処理ではない。実際の要求間の経過時間も保存する。再開後の最初の要求や保存応答の再利用は、途切れずに実行された標本と区別する。

これは各条件4件の小規模な診断であり、実行順序の影響も分離していない。通信の原因を断定したり、安定した遅延の分布を推定したりするための試験ではない。5秒は診断用の待ち時間で、対局の2秒という持ち時間は変更しない。回答が得られた場合に、2秒枠内での待ち時間配分を見直す材料にする。

APIの不正応答、HTTPエラー、ネットワーク障害、5秒でのタイムアウトなどが起きたら、その時点で診断を停止する。同じコマンドを再実行しても、完了・障害済みの要求を再送しない。障害後に別の要求IDを作って繰り返す機能はない。

## 費用と既存記録

追加プログラムはキット0.1.0の予算台帳とAPIクライアントをそのまま使う。元の3件のタイムアウト予約額を保持していることを確認してから実行する。台帳が見つからない場合は、新規作成せず停止する。予備試験の合計枠$0.40、通常枠$4.50、全体上限$5は維持する。

2026年9月21日に再確認した[公式モデル仕様](https://docs.typesafe.ai/models)は、`jev-1.13.0`の入力100万トークン当たり$0.042、出力無料、要求上限64kトークンである。既存キットと同様、送信前に65,536トークン分の$0.002752512を予約する。8要求で新たに予約し得る額の合計は$0.022020096で、今回受領した記録からの累計は最大$0.031394958となる。正常な使用量が返った分は実使用量による計算額へ更新する。これらはサービスの確定請求額ではない。

追加ファイルは本書、`latency-diagnostic.cjs`、`latency-diagnostic-manifest.json`の3つだけである。元のキットのプログラムと設定、停止した対局、過去の応答・局面記録は保持する。診断用に新しい要求・応答を保存し、既存台帳へ追記する。

診断の集計は`results/diagnostics/latency-diagnostic-v1.json`へ保存する。既存の`results/summary.json`は予備対局が停止した時点の記録として保持するため、診断後の累計費用は新しい診断ファイル、または元の`status`コマンドで確認する。

正式測定は未開始である。結果にかかわらず正式採用、公開配信、AI世代の更新は行わない。

## ローカルでの実行

配布ZIPをリポジトリのルートへ展開する。APIキーを設定した前回と同じターミナルを使う。

```bash
cd "$HOME/github/bao-la-kiswahili-game" &&
python3 -m zipfile -e bao-jev-latency-diagnostic-v1.zip . &&
node tools/jev-comparison/latency-diagnostic.cjs preflight &&
node tools/jev-comparison/latency-diagnostic.cjs run --live
```

`preflight`では、基準コード、追加ファイル、停止した対局、既存の費用予約を無課金で確認する。成功したときだけ後続の診断を開始する。キーが未設定なら通信前に停止する。その場合は、キーをチャットへ貼らず、非表示入力で設定してから同じ診断を実行する。

```bash
read -rsp 'Jev API key: ' TYPESAFE_API_KEY &&
printf '\n' &&
export TYPESAFE_API_KEY &&
node tools/jev-comparison/latency-diagnostic.cjs run --live
```

完了または停止後、結果をまとめて共有する。

```bash
cd "$HOME/github/bao-la-kiswahili-game" &&
python3 -m zipfile -c bao-jev-latency-results.zip tools/jev-comparison/results
```

通常は1分程度以内の診断である。`Ctrl+C`を1回押すと実行中の要求を記録して停止し、同じコマンドで未実行分から再開できる。2回押すと強制終了する。強制終了後のロックや中断記録は、元のキットの方針に従って保持する。

## 配布前の検証

Linux、Node.js v24.19.0で、受領した棋譜・要求・応答と模擬通信を使った18項目の検証を通過した。実API呼び出しは0回、検証によるAPI費用は0ドルである。

- 8件の入力、2条件の入力の一致、4回の4秒待機の指定を確認した。
- 全件成功時に8件だけが新規計上され、過去3件の不明分の予約額が残ることを確認した。
- 同じ診断を再実行しても追加送信せず、元のすべての結果ファイルが変わらないことを確認した。
- 3件終了後の一時停止から、残り5件だけを送ることを確認した。
- 応答だけ保存されている中断では保存応答を再利用し、応答がない中断では再送せず費用予約を保持することを確認した。
- タイムアウトとモデル不一致で停止し、予備試験の費用枠に達した後は送信前に停止することを確認した。
- 固定ファイルの変更、診断条件の変更、元の棋譜の変更を検出した。
- コマンドの無課金確認、`--live`不足、キー未設定、ブランチ不一致、既存台帳の欠落による停止を確認した。コマンド検証時のGit応答は模擬値であり、ユーザー環境の実際のGit状態はローカルの`preflight`で検証する。
- 模擬APIキーが結果・予算台帳に残らないこと、JavaScriptの構文を確認した。
