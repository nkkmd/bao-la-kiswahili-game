# API待ち上限1.5秒での予備対局

作成日: 2026年9月21日。条件の識別子: `pilot-matches-v2`。

## 遅延診断から分かったこと

最大5秒待つ追加診断では8件すべて正常に応答した。入力・応答・診断条件のハッシュ、使用量と費用集計は整合していた。過去の28件の要求について、基準エンジンから入力を再生成し、保存内容との一致を確認した。以前の予備対局・局面試験・遅延診断前の進捗集計は変わっていない。

| 入力 | 連続送信 | 4秒間隔の送信 |
| --- | ---: | ---: |
| 対局0手目の局面 | 1,078ms | 966ms |
| 対局2手目の局面 | 1,230ms | 549ms |
| 対局4手目の局面 | 512ms | 466ms |
| 比較用の局面試験0番 | 391ms | 509ms |

8件のAPI応答時間の中央値は531ms、範囲は391〜1,230msで、6件が500msを超えた。4秒待機を指定した送信の実際の間隔は約4.012〜4.017秒だった。すべて同じプロセス内で新たに送信した記録で、保存応答の再利用はない。

APIの入力使用量が返った分による累計計算額は$0.001677018、過去のタイムアウト3回に対する予約額は$0.008257536、合計計上額は$0.009934554である。追加診断8件による増加は$0.000559692だった。これらは実験台帳の計算額で、サービス提供者の確定請求額ではない。

今回の観測から、500msの待ち時間では多くの回答を受け取れないことが分かった。一方、各条件4件で、送信順序や時刻、接続の状態などの影響を分離していないため、遅延の原因は断定しない。この標本はnamuaの4局面に限られ、別の局面や時間帯も同じ遅延になるとは限らない。

## 今回固定する対局条件

API待ち上限を1,500msにする。これは今回の最大応答時間約1,230msに余裕を加え、Jevの回答を使える対局を測るための予備条件である。勝率を見て選んだ値ではない。今後のすべての要求が1,500ms以内に返ることを保証しない。

| 項目 | 今回の条件 |
| --- | --- |
| 基準AI | 固定コミットのAI-GEN4、expert／ビングワ、評価器PBAI-C015-v1 |
| 比較対象 | 同じAI-GEN4にJevの探索順序の提案を加えた候補 |
| モデル | `jev-1.13.0` |
| 各着手の全体の時間枠 | 双方2,000ms |
| API待ち上限 | 1,500ms。準備後の残り時間が少なければ短縮 |
| 最大探索深度 | 12 |
| 予備対局数 | 4組8局。同じ開始局面で担当側を交換 |
| 開始局面 | 以前に定めた4局面。namuaとmtajiが各2組 |
| 各対局の上限 | 開始局面から256着手 |
| 予備試験全体の費用枠 | $0.40。接続確認を除く、これまでの局面・対局・遅延診断を含む |
| 実験全体の予算 | 通常枠$4.50、余裕$0.50、上限$5 |

全体の2秒には、合法手生成、入力作成、通信、応答検証、費用記録、探索を含める。通信が1.5秒かかれば、準備や記録の時間も差し引いた残りで探索する。時間切れ時は、Jevの回答を使わず、その着手の残り時間で通常のAI-GEN4探索を続ける。使える時間がなければ合法な既定手を返す。同期処理によるわずかな期限超過は測定・保存する。

Jevの回答を受け取れるようになっても、通信のために探索が浅くなり、結果が悪化する可能性がある。その影響を含めて比較する試験である。自動のAPI再試行、有料の事前接続、対局前の通信による準備は加えない。

## 旧条件の記録と予算の扱い

500msの旧条件で停止した5手はそのまま保持する。新条件は各対局の開始局面から測り直す。新旧の手を1つの棋譜へつなげたり、新条件の成績へ旧条件の結果を加えたりしない。旧条件で生じた費用予約は全体の台帳に残す。

追加ファイルは本書、`pilot-v2.cjs`、`pilot-v2-manifest.json`の3つである。元のキット0.1.0、設定ファイル、遅延診断の追加プログラムを変更しない。`pilot-v2.cjs`が、API待ち上限だけが異なる条件を明示的に持つ。盤面の規則、評価器、APIへの入力、応答検証、探索順序の処理、料金・予約方式には元の実装を使う。

実行条件と開始局面は、最初の無課金確認時に`results/pilot-v2/plan.json`へ固定する。新しい棋譜は`results/pilot-v2/games/`、進捗集計は`results/pilot-v2/summary.json`へ保存する。既存の`results/summary.json`は旧条件の記録として保持する。API要求・応答には`pilot-v2-`で始まる新しいIDを使い、既存台帳へ追記する。

新しいコマンドは、旧条件の停止棋譜、完了した遅延診断、その費用が同じ台帳に残っていることを確認してから実行する。台帳のリセットや費用枠の増額は行わない。要求を送る前に最大額を予約し、予算枠を超える送信を止める。

## 実行と結果の共有

ZIPを`~/github/bao-la-kiswahili-game`直下に置き、前回と同じターミナルで実行する。

```bash
cd "$HOME/github/bao-la-kiswahili-game" &&
python3 -m zipfile -e bao-jev-pilot-v2.zip . &&
node tools/jev-comparison/pilot-v2.cjs preflight &&
node tools/jev-comparison/pilot-v2.cjs run --live
```

`preflight`は無課金で、基準ファイル・既存記録・予算台帳・開始局面を検証する。キーが未設定の場合は有料送信の前に停止する。必要ならAPIキーを非表示入力で設定し、同じ対局コマンドを実行する。

```bash
read -rsp 'Jev API key: ' TYPESAFE_API_KEY &&
printf '\n' &&
export TYPESAFE_API_KEY &&
node tools/jev-comparison/pilot-v2.cjs run --live
```

完了または自動停止したら、結果をまとめる。

```bash
cd "$HOME/github/bao-la-kiswahili-game" &&
python3 -m zipfile -c bao-jev-pilot-v2-results.zip tools/jev-comparison/results
```

8局がすべて256手まで続き、各手で2秒使った場合、対局処理だけで約68分となる。終局や予算・障害による停止で短くなる。各10手と終局時に進捗を表示し、棋譜は1手ごとに保存する。

`Ctrl+C`を1回押した場合は現在の着手を保存して停止する。同じコマンドで保存棋譜を再生・検証してから未完了分を再開できる。応答を受けた後、棋譜へ保存する前に中断した場合は再送せず、保存済みのAPI待ち時間を探索時間から差し引いて`recovered`として記録する。2回押すと強制終了する。残ったロックは、元のキットと同じ確認手順で扱う。

Jev側でAPIの代替処理が3回続いた場合は、自動停止する。この理由で止まった棋譜は、同じコマンドを再実行しても追加通信へ進めない。結果を共有し、原因と設定を確認する。手動停止からの再開でも、直前の連続失敗回数は引き継ぐ。

256手に達しても勝敗が決まらない対局は`UNRESOLVED`、エンジンの連続種まき上限で終了した対局は`ENGINE-LIMIT`として扱う。引き分けや負けへ自動変換しない。API障害、代替処理、深さ、所要時間、費用は成績と合わせて記録する。

## この段階の位置づけ

本試験は予備測定であり、正式測定は未開始である。4組の成績だけで僅差や同等性を判断しない。Jevの回答を対局に使える割合、探索時間・深さ、対局長、費用を確認して、次段階の実行数と条件を固定する。条件が成立しなければ、その限界も性能確認の結果として記録する。

結果にかかわらずJevは正式採用せず、公開配信、AI世代の更新、mainへの統合は行わない。

## 配布前の検証

Linux、Node.js v24.19.0で21項目の検証を通過した。実API呼び出しは0回、検証によるAPI費用は0ドルである。

- 元の設定が500msのまま、新しい条件だけが1,500msであることと、4組8局の担当側の交換を確認した。

- 持ち時間がない場合と合法手が1つの場合に、APIを送信しないことを確認した。
- 基準エンジンを深さ1に制限した模擬対局で8局・288手を完了し、棋譜を再生して確認した。模擬API要求は112件だった。この数字は実際の2秒対局の結果や必要な要求数の予測には使わない。

- 応答が保存された直後に中断した場合、棋譜のない着手を再開してもAPI要求を再送せず、保存応答の待ち時間を差し引くことを確認した。
- モデル不一致と予算枠到達時の停止、固定条件や担当側の不一致の検出、過去のタイムアウト予約額とすべての既存結果ファイルの保持を確認した。
- 無課金確認、`--live`不足、キー未設定、ブランチ不一致、台帳欠落時の停止を確認した。コマンド検証のGit応答は模擬値であり、ユーザー環境の実際のGit状態はローカルの`preflight`で検証する。
